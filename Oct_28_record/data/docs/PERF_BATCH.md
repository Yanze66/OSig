# 批处理吞吐（2026-10-26，100 MHz 镜像，server cmd 9 PBS_BATCH）

一条命令带 n 个密文：n 条 LD → n 条 PBS（只有最后一条带 flush 位，序列器按 BATCH_PBS_NB=8 分批、TOTAL_PBS_NB=16 在飞行中）→ n 条 ST。
pbs_cycles 只计 PBS 阶段（第一条 PBS 推入到最后一条 pep ack）。往返由 Ubuntu 客户端计时。

| 批量 n | LUT | 每密文硬件周期 | 每密文硬件时间 | 每密文往返 | 解密校验 |
|---|---|---|---|---|---|
| 1（单发） | MsgOnly | 794,219 | 7.94 ms | 8.85 ms | 10/10 |
| 8 | MsgOnly | 113,924 | 1.14 ms | 1.71 ms | 10/10 |
| 16 | MsgOnly | 113,091 | 1.13 ms | 1.66 ms | 10/10 |
| 16 | BwAnd | 113,266 | 1.13 ms | 1.67 ms | 16/16 |
| 32 | MsgOnly | 112,884 | 1.13 ms | 1.64 ms | 10/10 |
| 32 | BwAnd | 112,828 | 1.13 ms | 1.66 ms | 16/16 |

结论：
- 批量 8 已把 PE 流水线填满，8/16/32 的每密文周期一致（约 113k），批量 16 的总周期正好是批量 8 的两倍，说明现在是数据通路（PSI16 NTT @100 MHz）的算力上限，不再是 DDR 延迟。
- 相对单发提升 7.0 倍（硬件）/ 5.4 倍（往返）。往返比硬件多约 0.5 ms/密文，是 TCP 传 2×16 KB 密文和 XRT 同步的开销。
- 相对 CPU 单线程 tfhe-rs（15.0 ms）：硬件 13.3 倍，往返 9.1 倍。
- 200 MHz 镜像若时序收敛，每密文硬件时间预期约 0.57 ms。

原始数据：build_kernel/perf_batch/*.txt。

### 修正后的性能模型（取代上面"t = c/f + m"的加性拆分）

把 bpbs8 / b16 / b32 在 100 与 200 MHz 的全部数据放在一起，每个硬件批次的时间是
**max(密钥流时间, n × 113.5k 拍)**，两者重叠而不是相加：

- 密钥流时间：200 MHz 下约 6.6 ms（1.32M 拍，BSK 57.6 MB + KSK 43 MB ≈ 15 GB/s），100 MHz 下 7.9 ms（AXI 4 口 × 256 bit × 100 MHz 的口速上限）。
  一批不管 n 多少都读一遍，所以 n ≤ 8 时总时间平坦在 1.32M（bpbs8 的 8/16/32 批量都是 167k/密文，单发 1.32M，都是它）。
- 算力时间：每密文 113.5k 拍，与频率无关（100 MHz bpbs8 批 8 也是 113.9k/密文）。113.5k = LWE_K 879 轮 × 129 拍，
  而 NTT 核是 R=2 × PSI=16 = 每拍 32 个系数，每轮每密文要做 (k+1)=2 个 N=2048 多项式 = 4096/32 = 128 拍。**算力项就是 NTT 吞吐。**
- 交点：200 MHz 下 1.32M / 113.5k ≈ 11.6 个密文。批深 ≥ 12 就已经完全是算力（NTT）瓶颈，b16 已经拿到全部收益，b32 多出的 BRAM（77%）白花。
- 之前从 100/200 MHz 两点拟合出的"59k 拍 + 0.54 ms"是两个工作点都落在不同区域（100 MHz 算力瓶颈、200 MHz 密钥瓶颈）造成的假象。
