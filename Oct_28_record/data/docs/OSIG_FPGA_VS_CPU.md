# OSig 服务端：VCK190 hpu_mini 对比高端 CPU（2026-10-27）

主线任务的第一阶段结论：把 OSig 的瓶颈步骤（整流 rectification、相关性检查 pertinency check，以及过滤 filter）
的全部 KS+PBS 搬到 VCK190 上的 hpu_mini 之后，10 个接收者的服务端处理（Alg4）从 CPU 的 52.7 s
降到 22.2–22.5 s（200 MHz）/ 26.8 s（100 MHz），结果与 CPU 逐位一致。本文记录数据、方法与解读；优化留到下一步。

## 1. 比较对象

| | CPU 基线 | FPGA 路径 |
|---|---|---|
| 程序 | `obsig-tfhe --run-dir runs/bench_r10` | 同一二进制加 `--fpga 192.168.50.2:5002` |
| 参数 | v1_4_hpu_879_ks32_tuniform_2m128（N=2048, k=1, LWE 879, PBS 23/1, KS 2/8, KS32） | 同 |
| 工作负载 | G=25, Q=10, R=10, V=4：10 个接收者，每轮 10 条消息，16 位标签 + 2 位信号 | 同（同一份 runs/bench_r10 的密钥与消息） |
| 处理器 | Intel i9-14900K（24 核 32 线程），tfhe-rs 1.8.1，x86 FFT，rayon 对 10 个收件箱并行 | 同一台机器做主机，PBS 发到板子 |
| FPGA | — | VCK190（xcvc1902），hpu_mini：单 PE、PSI16 NTT、BATCH_PBS_NB=8 / TOTAL_PBS_NB=16，密钥驻留板上 DDR |
| 连接 | — | 千兆直连（eno2 ↔ end0），TCP 协议 HPQ1，命令 9 PBS_BATCH 一次最多 32 个密文 |
| 分工 | 全部在 CPU | 4.1 整流、4.2 相关性 AND 链、4.3 过滤乘法的 PBS 在 FPGA；打包、累加（smart_add）、4.4 收件箱更新（cmux）仍在 CPU |

PBS 数量：CPU 基线 15,680 次全在 CPU；FPGA 路径 14,400 次在板上、1,280 次（收件箱更新）在 CPU。

## 3. 正确性

- 200 MHz 板上 step2 向量：MsgOnly 10/10（单发、批 8/16/32），BwAnd 16/16（单发、批 16/32），`verify_hw_outputs.sh` 解密比对。
- OSig `--verify-io -r 4`（4 个接收者，16 个匹配对 + 48 个非匹配对）：100 MHz 与 200 MHz 都是 4/4 `FINAL_INBOX_PASS`、`OSIG_HPU_CPU_VALIDATION_PASS`；
  校验内容包括整流后的标签、PI、过滤后的信号与收件箱更新，与 CPU 路径一致。日志 `logs/fpga_verify_r4.log`、`logs/fpga_verify_r4_200mhz.log`。
- 时钟核实：内核 CYCLE 计数器对墙钟 2 s 测得 200.25 MHz（换 BOOT.BIN 之前只换 xclbin 时测得 99.9 MHz）。

## 4. 解读

1. **端到端 2.3–2.4×。** 这是最保守的比较：CPU 一侧已经用 rayon 并行 10 个接收者，FPGA 一侧只有一个 PE 且串行服务 10 个线程。
   收件箱更新（1,280 次 PBS，约 18 s worker）仍在 CPU，占 FPGA 路径 worker 时间的 10%。
2. **频率翻倍只换来 1.18×（单发）/ 1.36×（批量）。** 每密文周期从 113k 涨到 167k（批量）、789k 涨到 1,337k（单发）。
   按 t = c/f + m 拆分：批量每密文约 59k 周期随频率缩放、0.54 ms 不随频率变（约占 200 MHz 下的 65%）；单发约 240k 周期缩放、5.5 ms 不变。
   不变的部分就是 BSK/KSK 从板上 DDR 的流式读取（每个 PBS 批次读一遍 ~101 MB 密钥）。
   **结论：当前瓶颈是密钥带宽，不是 NTT 算力。** 下一步优化应优先减少 DDR 密钥读取（更大的 BSK/KSK 片上缓存、跨批次复用、按接收者分组调度），其次才是时钟或更多 PE。
3. **OSig 中每密文 214k 周期高于微基准的 167k**，原因是相关性 AND 链每轮只有 10 个密文（一个接收者一轮 10 条消息），
   序列器按 8 个一批，10 = 8 + 2，尾批只填了四分之一；整流和过滤批次（160 个 / 20 个密文）能填满。
   把多个接收者或多轮的密文合并到同一批（受密钥槽切换限制：换接收者就换密钥）是纯软件层面的改进。
4. **主机侧开销可见。** 批量 32 的往返比硬件多 0.55–0.60 ms/密文（TCP 传 2×16 KB 密文、XRT 同步、服务端拷贝）。
   200 MHz 下硬件时间只剩 0.83 ms，这部分已占往返的 40%；板子忙碌占比从 75% 降到 69%，剩余时间是主机的打包/累加和排队。

## 5. 做法要点（复现时需要）

- 数据打包：与 tfhe `smart_evaluate_bivariate_function` 一致，v = 2·x + pi，pi 在最低位；自定义 LUT gid 40（AND2）与 41（MUL2）。
  其他接收者的"垃圾"密文整流后值的填充位可能为 1（如 30 = −2），pi 放最低位时 pi=0 仍是吸收元，与 CPU 行为一致；4·pi + x 的打包会泄漏非零值。
- 密钥槽：板上 server 有 16 个密钥槽，OSig 把第 i 个接收者放到槽 i。step2 的 `hpu-client load-keys` 用槽 0，OSig 跑过之后槽 0 已被接收者 0 覆盖，
  再测 step2 向量前必须重新 `load-keys`（否则解密全错，但硬件无报错）。
- 板上 CMA：10 个接收者的密钥共约 1 GB，需要 `uEnv.txt` 里 `cma=1536M`（低 2 GB 区域，命令行 CMA 不能到 2 GB）。
- 换时钟必须换 BOOT.BIN：VCK190 base 是 flat 平台，运行时 `load_xclbin` 只加载元数据，PL 来自启动分区 BOOT.BIN 里的 PDI。
  200 MHz 的 BOOT.BIN 与 xclbin 在 `step2_pbs_core/build_kernel_200/package/`。
- 日志：`logs/cpu_baseline.log`，`logs/fpga_bench_r10_100mhz{,_run2}.log`，`logs/fpga_bench_r10_200mhz{,_run2}.log`，
  `logs/fpga_verify_r4{,_200mhz}.log`，`logs/cpu_verify_r4.log`。

## 6. 硬件批深 16（2026-10-28 补充，bpbs16_tpbs32 镜像，200 MHz）

第 4 节的结论是密钥带宽瓶颈，所以第一个优化是把序列器的硬件批深 BATCH_PBS_NB 从 8 提到 16（TOTAL 16→32），
每个批次 BSK/KSK 只从 DDR 流读一遍，每密文密钥流量减半。RTL 不改，只换 pep_batch_definition_pkg（`step2_pbs_core/scripts/gen_cfg_flow.py --cfg b16`），
200 MHz 时序收敛（WNS +0.082 ns），BRAM 56%→58%。

| 指标 | bpbs8（200 MHz） | bpbs16（200 MHz） | 变化 |
|---|---|---|---|
| 微基准批 16/32 每密文硬件 | 167k 周期 = 0.83 ms | 113k 周期 = 0.57 ms | 0.68× |
| 微基准批 32 每密文往返 | 1.38–1.43 ms | 1.15 ms | 0.82× |
| 单发 | 1,337k = 6.69 ms | 1,323k = 6.61 ms | 不变 |
| OSig 每密文硬件（FPGA_STATS） | 214.2k = 1.07 ms | 129.5k = 0.65 ms | 0.61× |
| OSig Alg4 wall | 22.2–22.5 s | 15.9–16.0 s | 0.71× |
| 相对 CPU 52.71 s | 2.35× | 3.30× | |
| 板子忙碌占比 | 69% | 59% | |

- OSig 每密文 129.5k 比微基准高 15%：相关性 AND 链每轮只有 10 个密文，10 < 16 仍是一个半满批次（之前是 8 + 2 两个批次，所以收益反而最大：4.2 从 93.5 s 降到 53.0 s）。
- 板子忙碌占比降到 59%，主机侧（打包、累加、cmux、TCP 排队）已经是一半以上的墙钟。
- 正确性：step2 向量单发/批 8/16/32 全对；`--verify-io -r 4` 4/4 `FINAL_INBOX_PASS`、`OSIG_HPU_CPU_VALIDATION_PASS`（`logs/fpga_verify_r4_b16.log`）。
- 日志：`logs/fpga_bench_r10_b16_run{1,2}.log`；微基准原始数据 `step2_pbs_core/build_kernel_b16/perf_batch/`。

### 6.1 批深 32：没有进一步收益，瓶颈已变成 NTT 吞吐

bpbs32_tpbs48 镜像（BRAM 77%，WNS +0.136 ns）上板后，微基准每密文从 n=16 到 32 都是 113.5k 拍，与 b16 一模一样；
OSig Alg4 15.74–15.76 s（3.35×），每密文 125.0k，只比 b16 好 3%（来自 20 个密文的过滤请求：b16 下是 16 + 4，4 个的尾批按整条密钥流计时；b32 下是一批）。
verify-io 4/4 通过（`logs/fpga_verify_r4_b32.log`）。

中间踩了一个坑：server 的 BPIP 超时 50 µs 比串行推 32 个 DOp 还短，序列器把 32 个截成 24 + 8，第一次测 b32 时 n≥28 每批固定 4.03M 拍，
OSig 16.18 s 与 b16 持平（`logs/fpga_bench_r10_b32_timeout10k.log`）。server 改成 5 ms 超时后才得到上面的数据。

把 bpbs8 / b16 / b32 在 100 与 200 MHz 的数据放在一起，**每个硬件批次的时间 = max(密钥流时间, n × 113.5k 拍)**，两项重叠而非相加：
密钥流 200 MHz 下约 6.6 ms（1.32M 拍），每密文 113.5k 拍 = LWE_K 879 轮 × 128 拍，正是 NTT 核（R=2 × PSI=16，每拍 32 个系数）
处理每密文每轮 2 个 N=2048 多项式的吞吐。交点约 12 个密文：批深 ≥ 12 后就是 NTT 算力瓶颈，b16 已经拿到全部收益。
第 4 节"瓶颈是密钥带宽、不是 NTT"的结论只对 bpbs8（每批 8 < 12）成立；第 4 节的"59k 拍 + 0.54 ms"加性拆分是两个工作点分别落在密钥区与算力区造成的假象，已被 b32 数据推翻。

下一步按计划做 NTT：PSI 16→32 理论上把算力项减半到 57k 拍/密文（LUT 现在 40%），交点变成 23 个密文，届时 b32 才有用；
另一条路是在 AIE 上做 NTT 或加第二个 PE。推荐部署镜像：b16（资源与 bpbs8 几乎相同）。详细数据：`step2_pbs_core/doc/PERF_BATCH.md`。

## 7. 还没做的

- 没有测更多接收者（R>10）：CPU 有 32 线程，R 增大时 CPU 会继续按核数扩展，而单 PE 的板子不会；这个比较在 R=10 对 FPGA 最有利。
- 收件箱更新（cmux）还在 CPU；搬过去再省约 10% worker 时间。
- 优化（密钥缓存、批次合并、第二个 PE、AIE NTT）按约定放在下一步讨论。
